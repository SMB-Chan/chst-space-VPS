# OpenAI / Alibaba 凍結・Xiaomi MiMo 追加の監査

監査日: 2026-09-09（JST）
対象: `026619f` 時点の実装と今回の修正。既存の未追跡ファイルは変更していない。

## 発見と修正

| 重要度 | 不具合 | 修正 |
| --- | --- | --- |
| 高 | 凍結したプロバイダをモデル検出対象から外しても、カタログ統合が未指定プロバイダを復活させる | 統合対象を明示し、資格情報・凍結・OpenRouter予算による最終フィルタを適用。凍結先のモデル一覧APIも呼ばない |
| 高 | チャット以外の画像読取り・ファイルレビュー・音声認識・Alibaba専門能力が凍結先を呼べる | 共通の凍結判定を追加。直接のモデル解決を拒否し、補助画像処理は利用可能なプロバイダへ切替。Alibaba専門能力の資格情報解決も停止 |
| 高 | MiMoにもAlibaba用 `incremental_output` を送り、思考オフが効かない | MiMo専用の `thinking.type` と `max_completion_tokens` を適用。検索判断400、能力判断800など内部処理の出力上限も統一 |
| 高 | MiMoのツール応答継続で `reasoning_content` が失われる | ストリームから得た推論をサーバー内部のツール情報に保持し、検索・専門能力の継続リクエストに引き継ぐ。ユーザー向け本文には出さない |
| 中 | 思考のみ・空の応答の再試行でもMiMoの思考が有効なまま | 空応答の再試行は思考を明示的に無効化し、指定済みの出力上限を維持 |
| 中 | MiMoのキー未設定でもモデルが表示され、能力表示はDashScopeの有無に依存 | MiMo自身のクライアント・モデル一覧で利用可否を判定。キー名の優先順位と空白処理も修正 |
| 中 | 凍結モデルの保存済み設定が送信先に残り、表示と実際のリクエストがずれる | サーバー一覧取得後、利用可能なモデルへ送信先と表示を揃える。APIのモデル省略時も利用可能なモデルを選ぶ。空の一覧では送信を止める |
| 中 | OpenAIを凍結してキーを削除すると、MiMoだけでもサーバー起動が失敗 | OpenAI凍結中はOpenAI資格情報を必須にしない |
| 中 | OpenAPIと生成済みZod・クライアント型がMiMo/OpenRouterを許容しない | 元の仕様にプロバイダ・推論種別を追加し、コード生成を実行 |
| 中 | ローカル `.env` と `.replit` の共有起動設定に凍結フラグがない | 両方に `DISABLE_OPENAI_MODELS=true` / `DISABLE_DASHSCOPE_MODELS=true` を追加 |
| 低 | MiMo/OpenRouterの回路遮断エラーがOpenAIと表示される | 実際のプロバイダ名を表示 |

## 運用反映

修正はローカル作業ツリーに反映済み。本番デプロイ・稼働中サーバーの再起動は実施していない。反映時は新しいコードと凍結フラグを適用し、サーバーを再起動する。解除する場合は対象フラグを `false` に戻して再起動する。

OpenRouterは既存の一般ユーザー制限・予算制御を維持する。MiMoは既存の管理者向けプロバイダとして追加される。凍結中のOpenAI・Alibabaへの課金を伴う診断リクエストは送っていない。
